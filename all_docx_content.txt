Executive Summary
The Barcode Bill Scanner App is an Android mobile application designed to streamline bill creation and product documentation. Users can create detailed bills with multiple products, capturing serial numbers through barcode scanning and manual entry, then export the complete bill as a PDF document.
Key Features:
Barcode scanning for serial number capture
Multi-product bill creation with unlimited products
Dynamic serial number field generation based on quantity
Offline functionality (no internet required)
PDF export with date/time metadata and bill ID
Local bill storage for viewing, editing, and duplication
1. Core User Workflow
The app follows a linear, step-by-step workflow to ensure all required data is captured before bill finalization.

2.2 Optional Fields

2.3 Field Unlock Sequence

Product Name entered → Quantity, Model Number fields unlock
Quantity entered → Serial Number entry tabs appear (equal to quantity)

Industry-specific serial number barcodes (e.g., Code128, Code39)
3.2 Scanning Process
For each Serial Number entry tab:
User can tap the camera icon next to the serial number field
Camera opens fullscreen, covering the entire form
App detects and scans the barcode
On success: Serial number auto-populates and focus moves to next serial number field
3.3 Scan Error Handling
3.4 Duplicate Serial Number Prevention
If a serial number (scanned or manual) already exists in the current product:
Warning message displayed: "This serial number already exists in this product"
User can still proceed (allow duplicates within warning)

On first app launch, a system permission dialog requests camera access:
User grants permission → Camera icon enabled
User denies permission → Camera icon disabled, message shown: "Camera permission required. Enable in Settings."
Manual entry still available for all serial numbers
3.6 Manual Serial Number Entry
Serial numbers can always be entered manually by typing into the field:
No validation format enforced (alphanumeric allowed)
Duplicate warning shown (same as scanning), but entry allowed
4. Serial Number Management
4.1 Dynamic Tab Generation
When user enters a quantity value, the app automatically creates that many serial number entry tabs:
Example: Quantity = 3 → Three tabs labeled "Serial 1", "Serial 2", "Serial 3"
Each tab has a text input field + camera icon for scanning
4.2 Quantity Change & Serial Number Removal
If user changes quantity from a higher to lower number (e.g., 3 to 2):
Dialog appears: "You have 3 serial numbers. Quantity is now 2. Select which serial number to remove:"
User selects which serial number to delete
Selected serial number removed, tabs regenerated
5. Product Management
5.1 Adding Multiple Products
Once all mandatory fields are completed for a product:
"Add Another Product" button appears below the form
Clicking it creates a new product section (same form repeats below with Product Name field active)
5.2 Product Limits
Maximum 20 products per bill. No explicit limit shown; app prevents adding beyond 20 with message: "Maximum 20 products per bill reached."
5.3 Product Editing
After adding a product, users can:
Edit any field by tapping into it
Delete the entire product by tapping a Delete button at the top-right of the product section
Product label shows "Product 1", "Product 2", etc.
5.4 Product Deletion & Undo
When user deletes a product:
Product is immediately removed from the form
"Undo" button appears (allows undoing only the most recent deletion)
Undo button disappears after a new action is performed
5.5 Duplicate Product Names
Multiple products can have the same name. No duplicate prevention or warning is implemented.
6. Form Validation & Bill Submission
6.1 Validation Rules
A bill can only be saved if:
At least one product is added
All mandatory fields (Product Name, Model Number, Quantity, Serial Numbers) are filled
All serial number fields have values (no empty tabs)
6.2 Validation Summary on Save
When user taps the Save button:
App validates all fields
If validation fails, a summary dialog appears listing all missing/invalid fields
Dialog does NOT auto-scroll to first error; user manually navigates
If validation passes, bill is saved and PDF preview screen appears

All development work on BillItUp must adhere to the following non-negotiable principles:

UI/UX must remain smooth, modern, responsive, and visually clean throughout all changes.
No lag, jittering, layout shifts, broken animations, or inconsistent spacing is permitted.
Frontend interactions must feel polished with smooth transitions and animations.
All edit logic must preserve data consistency and prevent accidental overwrites.
Changes must be implemented phase-by-phase to avoid introducing bugs.
All timestamps must use a consistent date-time format across the entire application.
All edit history and logs must be permanent and non-editable.
Bill structure and sequence numbering must never break, even after deletions.

1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) document formally defines the complete functional and non-functional requirements for the BillItUp application. It serves as the authoritative reference for developers, QA engineers, and stakeholders to understand exactly what the system must do, how it should behave, and what constraints govern its implementation.

1.2 Product Overview
BillItUp is a billing management application designed for businesses to create, manage, track, and export bills. The application supports structured bill numbering, product-level tracking with serial and model numbers, post-save editing controls, an audit log system, a daily daybook view, and PDF export functionality.

1.3 Intended Audience
Software Developers – for implementation guidance
QA Engineers – for test case preparation and validation
Project Managers – for progress tracking and scope management
Stakeholders / Business Owners – for requirements sign-off

1.4 Definitions & Abbreviations

2. Overall System Description
2.1 System Context
BillItUp is a web-based billing application accessible via modern browsers. It manages the complete lifecycle of a bill from creation, through editing (within permitted windows), to final locked archival and PDF export. The system maintains a permanent, immutable audit trail for all changes.

2.2 System Constraints
All edits are restricted to the same calendar date as bill creation.
Locked data cannot be unlocked or altered by any user role.
Edit logs cannot be deleted or modified under any circumstances.
Bill sequence numbers must be unique within any given calendar day.
The UI must remain responsive and performant on mobile, tablet, and desktop.

2.3 Assumptions & Dependencies
The application has an existing bill management backend that supports the described data model.
PDF generation capability is available in the technology stack.
The system clock is authoritative for all date-time calculations and restrictions.
Users have appropriate authentication and role-based access to interact with bills.

3. Functional Requirements
All functional requirements are organized by development phase. Each requirement carries a unique identifier, description, priority level (High / Medium / Low), and the phase it belongs to.

4. Non-Functional Requirements
4.1 Performance
The application shall load bill pages and the Daybook view in under 2 seconds under normal network conditions.
All animations (add/remove transitions) shall complete within 300ms to maintain a smooth UI experience.
The system shall remain performant for bills containing a large number of products and log entries.

4.2 Reliability & Data Integrity
The system shall prevent duplicate bill number generation under all conditions, including concurrent bill creation.
Edit locks must be enforced server-side; client-side enforcement alone is insufficient.
Quantity auto-calculations shall always be consistent with the current set of active (non-removed) serial numbers.
No data loss shall occur as a result of concurrent edits or network interruptions.

4.3 Usability
The UI must be responsive and fully functional on mobile, tablet, and desktop screen sizes.
All animations and transitions must feel smooth and modern — no visible lag or jitter.
Visual cues (red for removed, green for added, blue for log highlight) must be consistent across all screens and the PDF export.
Navigation between log entries and bill sections shall be intuitive and require no more than one click.

4.4 Security & Auditability
All bill data and logs must be stored securely and protected from unauthorized access.
Logs must be immutable — no API endpoint or database mechanism shall allow modification or deletion of log records.
Date-based edit restrictions must be enforced using server-side date validation, not client-side date checks.

4.5 Maintainability
Features must be implemented phase-by-phase as documented to minimize regression and logic conflicts.
Code architecture must support clean separation between bill creation, editing, locking, logging, and PDF export modules.
All timestamps must use a single consistent date-time format across the entire application stack.
